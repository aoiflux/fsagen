# Changelog

## Unreleased

Generator version is **7**. Through the work below, until the last section,
nothing changed a byte an existing input produces, and every v6 golden for an
untouched input stayed byte-identical (the four examples that gained tags
re-recorded only their ledger, answer key and dry-run listing). The one planned
bump is described under _Generator version 7_; `testdata/golden/v6/` stays
beside `v7/` until the owner retires it. The subcommand after it, `diff-oracle`,
only reads, and changes no generated byte; nor does the target abstraction
after that. FAT32, ext4 and NTFS disk images, last, are a new kind of output:
a run into a directory writes what it wrote before.

**Inputs that used to be refused are now accepted.** `.xlsx` was refused as a
format fsagen could not build; it now builds one (see _Macro-enabled Office
documents_).

**Inputs that used to be accepted are now refused.** An extension or a name
that promises a format fsagen now builds means that format, so the same name
given only `content_len` — filler under a name that promises a real artefact,
the silent wrong output this tool exists to prevent — is an error that asks for
the format's block, as `.exe` did when PE inference arrived:

- `.lnk` means `format: lnk`. `playbook-malware-lifecycle` had exactly that: its
  startup-folder `WindowsUpdate.lnk` is now a real shortcut to the dropper the
  scenario plants (941 bytes instead of 256). Its goldens were re-recorded on
  both platforms; one line of its corpus fingerprint moved, the shortcut's, and
  nothing else did. `examples/INVESTIGATION_WORKFLOW.md` shows the new size and
  MD5.
- `.pf` means `format: prefetch` and `.evtx` means `format: evtx`; `.hve` and
  the names `NTUSER.DAT`, `USRCLASS.DAT`, `SYSTEM`, `SOFTWARE`, `SAM`,
  `SECURITY` and `DEFAULT` mean `format: regf`; the names `utmp`, `wtmp` and
  `btmp` mean `format: utmp`, and `audit.log` means `format: auditd`. `.dat`
  alone infers nothing: it names plenty of files that are not hives (an
  example and the acceptance scenario stage `.dat` files).
  `playbook-comprehensive-ransomware` wrote 512 bytes of filler to
  `winevt/Logs/Security.evtx`; it is now the cleared Security log the scenario
  describes, holding the 1102 that says who cleared it (69632 bytes). Its
  goldens were re-recorded on both platforms; the log's line and the input hash
  moved, and nothing else did.

### ATT&CK tags and a Navigator layer

Any operation, playbook action or playbook step takes `mitre: [T1070.006, ...]`.
An action exhibits its step's techniques and its own. The IDs are checked for
shape only (`T1234` or `T1234.001`); fsagen does not embed the ATT&CK catalogue.
The ledger, the answer key and the dry-run listing carry each operation's
techniques, and a run with at least one tagged operation that ran writes
`mitre-layer.json` — an ATT&CK Navigator layer, format 4.5 — beside the answer
key, its digest recorded in the run manifest. A rerun without tags removes a
stale layer.

Tagging moves no byte. An action without an `id` takes its random key from a hash
of its own YAML; `mitre` is now left out of that hash, so the key is the same
tagged or not (`TestMitreLeavesRandomKeyAlone`, proved load-bearing by emptying
the exclusion; `TestMitreLayerWritten` compares the two corpora).
`playbook-log-tampering`, `-windows-ads-motw`, `-persistence-artifacts` and
`-insider-threat-exfil` are tagged. Their input changed, so their ledger, answer
key and dry-run goldens were re-recorded on Windows and under WSL; every one was
checked to differ only by the `mitre` fields and the `src` line numbers the new
lines shifted.

### Timesketch timelines

`--timeline-format timesketch` writes the JSON lines Timesketch imports: one
event per entry and known time, as Plaso's file-stat parser emits them, with
`message`, `datetime`, `timestamp_desc` (Plaso's names), `@timestamp`, integer
microseconds and the entry's attributes. Times finer than a microsecond are cut
down to it. It is chosen by name only, since `.jsonl` already means `jsonl`.
The format lists in `--help`, the flag's own help and its two error messages
are now built from the timeline package's format table rather than written out
by hand in four places.

### Windows shortcuts (`.lnk`)

`format: lnk`, inferred from `.lnk`, with an `lnk:` block, writes a shell link
as [MS-SHLLINK] lays it out: the header with the target's times, size and
attributes; the ID list down to the target, each folder an 8.3 name plus a
`0xBEEF0004` block with the long name; the LinkInfo with drive type, volume
serial, label and path (ANSI and, for a non-ASCII path, Unicode); the strings;
and the TrackerDataBlock with the machine name and the volume and object ids.
Times default to the operation's; serial, machine name and the NTFS file
reference are drawn from the operation's stream when not given.

It is read back three ways. A reader in the tests walks every structure from
the sizes and offsets the link gives. Windows' own shell resolves the target,
strings, icon and window state. And golnk, a third-party Go parser, reads it in
the new **conformance module** (`internal/conformance`), a separate Go module so
that test-only parsers never enter fsagen's `go.mod`; the gate now vets, tidies
and tests it. golnk turned out to read the header's access and write times the
wrong way round; which offset holds which was settled against a shortcut
Windows saves itself (`TestLNKHeaderTimeOrderMatchesWindows`), and fsagen
follows Windows and the specification.

The shared Windows encodings — FILETIME, GUIDs in their on-disk layout,
version 1 GUIDs, UTF-16LE, MS-DOS dates — now live in `libgen/winbin.go`;
`utf16z` and `dosTime` moved there from `pe.go` and `zipgen.go` unchanged.

### Slack canaries

A `create` or `update` takes `slack: {cluster_size, kind, fragment_of}` and
leaves bytes in the rest of the file's last cluster: a canary (a marker naming
the object, seeded text, the marker again at every sector boundary), the marker
repeated, or the first bytes of another file. The ledger and a new `slack`
answer-key fact record kind, cluster size, offset, length, SHA-256 and whether
the bytes were verified.

Slack is a capability. On live NTFS it is best effort: the file is written long,
flushed and shrunk back with `FlushFileBuffers` around `SetEndOfFile`, and the
record says `verified: false`, because only a raw read of the volume can confirm
it — `TestSlackSurvivesOnRawNTFS` in the conformance suite does that as an
administrator with Velocidex's go-ntfs, following the file's own data runs. A
file of 1 KiB or less (possibly MFT-resident), and a `cluster_size` that is not
the volume's (read with `GetDiskFreeSpaceW`), are refused. Every other live file
system refuses slack at pre-flight: ext4 zeroes a block's tail on truncate, and
tmpfs and btrfs keep none. With `--on-unsupported=skip` the file is written
without its slack and the run manifest records the dropped `slack` field.

**Deviations from the plan.** Slack applies to `create` and `update`, not
`append`: the model does not track a file's size, so where an appended file's
last cluster ends is not known before the run. `fragment_of` names a file that
still exists at that point in the scenario; one already deleted has no bytes
left to copy. A structured format (pe, zip, docx, ...) cannot take slack, as its
size is only known once it is built.

### Prefetch files

`format: prefetch`, inferred from `.pf`, with a `prefetch:` block, writes the
prefetch file Windows 10 (SCCA version 30, in its 1903 layout) or Windows 11
(version 31) keeps for a program: its name and path hash, run count, last eight
run times, the files it loaded and the volumes they were on, each volume named
`\VOLUME{<created>-<serial>}` as Windows names it. ntdll.dll and the program
are always listed. The hash is checked against two real Windows 10 prefetch
file names, and a file named `NAME.EXE-XXXXXXXX.pf` must match its program, or
the scenario is refused.

It is compressed as Windows compresses it: a `MAM` header and [MS-XCA]
LZ77+Huffman (XPRESS Huffman), by a new deterministic encoder in
`libgen/xpress.go` with length-limited canonical codes by package-merge.
Windows' own `RtlDecompressBufferEx` decodes everything the encoder writes, as
do a decoder written from the specification and go-prefetch's. The run count is
written where Windows 10 1903 and later keep it, and the field older files kept
it in is zero, so every parser reads one count: go-prefetch reads the older
field first, PECmd the newer when the field between them is set, which it is.

### Event logs (`.evtx`)

`format: evtx`, inferred from `.evtx`, with an `evtx:` block, writes a Windows
event log: the file header, 64 KiB chunks with their 64-bucket string and
32-bucket template tables, and each event as binary XML, its template defined
inline the first time a chunk uses it, names interned per chunk with Windows'
name hash, records padded to eight bytes, every CRC right. Events 4624, 4688,
7045 and 1102 are built in with Windows' own provider, channel, version, task,
keywords and data names and types (1102 as `UserData`); any other event names
its provider. Windows' own `Get-WinEvent -Path` renders every record to exactly
the XML the events describe, across several chunks, and Velocidex's evtx reads
every value back. Where Windows nests event data in a template of its own,
fsagen uses one template per event.

A `data:` map is a new kind of field for the template pass: its values are
rendered in key order, so random draws stay reproducible, and its keys stay
literal. Each repetition of a playbook action renders into a map of its own
(`TestEvtxRepeatedRendersEachTime`, proved load-bearing by removing the copy).

### Registry hives

`format: regf`, inferred from a hive's name or `.hve`, with a `registry:` block,
writes a version 1.5 hive: keys with their last-write times, values of the eight
common types (inline, in a cell, or in big-data segments), hash leaves sorted
the way Windows looks names up and an index of leaves past 512 subkeys, names a
byte per character when they fit (as Windows stores them), one shared security
descriptor, and a checksummed base block. `run`, `userassist` and `usbstor`
write those artefacts where their hive keeps them: the Run key; Explorer's
ROT13'd, known-folder-GUID UserAssist records with their 72-byte values; and a
USB stick's `Enum\USBSTOR` key with its install, arrival and removal times as
FILETIME device properties, plus the `Select` key. An artefact in the wrong hive
is refused.

Windows' own registry loads every hive the tests build, as an application hive
(`RegLoadAppKey`, which needs no administrator), and reads each key, value,
type and time back. It found one thing the format documentation does not say:
Windows drops a big value whose last segment cell holds less than a full 16344
bytes, so every segment is now written full, the last one padded. Velocidex's
regparser reads the hives too.

### Linux login records and audit logs

`format: utmp`, inferred from the names `utmp`, `wtmp` and `btmp`, writes
glibc's 384-byte `struct utmp`: boots, shutdowns, logins, logouts (taking their
login's line, id and pid) and, in btmp only, failed logins. A time after
2038-01-19T03:14:07Z does not fit its 32-bit seconds and is refused.
util-linux's `utmpdump` and `last` read the records back, `last` pairing each
login with its logout (run under WSL; skipped where they are not installed).

`format: auditd`, inferred from `audit.log`, writes auditd's raw log: an
`execve` as the kernel records it (`SYSCALL`, `EXECVE`, `CWD`, two `PATH`s,
`PROCTITLE`, one serial), and `USER_AUTH`, `USER_LOGIN` and `USER_START` as PAM
and sshd write them, with strings hex-encoded by the kernel's own rule. Serials
start from the seed and rise. `TestAuditLogReadByAusearch` runs `ausearch`
where it is installed; it was not on any machine this was tested on, so nothing
outside fsagen has read these logs yet.

In a playbook, a login record or audit event that names no user is the actor's.

### Conformance module

go-prefetch, evtx and regparser, all Velocidex's and Apache-2.0, join golnk and
go-ntfs in `internal/conformance`. Each was checked to be pure Go and to build
on the pinned toolchain before it was added.

**Deviations from the plan.** `.dat` is not inferred as a hive (see above). A
built-in event's data names are checked, but a name left out takes the value
Windows writes when it has none rather than being an error: requiring all 27 of
a 4624's would make the block unusable. EVTX writes one template per event
rather than Windows' nested event-data template. The prefetch block has no
`device_path`: a volume's name follows from its serial and creation time, and
the hash's volume number is `harddisk_volume`.

### Timestomp

A new action, `timestomp`, sets times the way anti-forensic tools do: its
`atime`, `mtime`, `ctime` and `crtime` are the `$STANDARD_INFORMATION` times,
set as `mace` sets them, and `fn_atime`, `fn_mtime`, `fn_ctime` and `fn_crtime`
are the `$FILE_NAME` times beside them. The model now carries `$FILE_NAME`
times for every object, following NTFS: all four at the time the object is
born, copied from its own times when it is renamed (which is how the
double-rename trick makes the two sets agree), and moved otherwise only by a
`timestomp`.

No live volume lets a program set a `$FILE_NAME` time, so the new capability
`FilenameTimes` is false on every one (the run manifest's
`filename_times_controlled` now reports it rather than a constant). An `fn_`
time is a pre-flight error there, or with `--on-unsupported=skip` is dropped
and recorded while the rest of the stomp runs.

The `stomped` fact of a `timestomp` adds `fn_times`, `fn_controlled` (false on
a live volume: the times are what the scenario means, not what is on disk),
`delta` (each `$STANDARD_INFORMATION` time minus its `$FILE_NAME` time, in
seconds, as an exact decimal) and `timestomp_detected` (the creation times
compared as MFTECmd's `SI<FN` column compares them). Its ledger entry and
`--dry-run` line carry `fn_times`. A `mace`'s fact, entry and line are
unchanged.

**Deviations from the plan.** The fact keeps `times` for the
`$STANDARD_INFORMATION` times, as `mace`'s does, rather than a new `si_times`.
Modelled timelines do not yet write `($FILE_NAME)` lines: they would only
appear where those times are controlled, which no live run is, and the csv
timeline would need a column for them. They come with the NTFS image target.

### Macro-enabled Office documents

`format: docm`, `xlsx` and `xlsm`, inferred from their extensions, write a Word
document with a VBA project, an Excel workbook (one sheet, its column A
holding the text a line to a row, at most 32767 characters a cell), and the
same workbook with a VBA project. `.xlsx` is no longer refused. The `docx`
block now also applies to `docm`, and a new `xlsx` block carries the same
properties for workbooks.

The project holds one macro, and it is inert: it assigns a marker string to a
local variable and does nothing else, and the new `vba` block can only choose
its entry point (`AutoOpen` or `Document_Open`; `Auto_Open` or
`Workbook_Open`), the standard module it sits in, and the marker, printable
ASCII without a double quote. It is written from [MS-OVBA] on a new
compound-file writer (`libgen/cfb.go`, [MS-CFB] version 3, every time zero,
an all-black tree) and a compressor that reproduces the specification's three
worked examples byte for byte. There is no p-code; Office compiles the source.

Read back by Windows' own structured storage (`StgOpenStorageEx`, in every
run of the suite on Windows), by mscfb in the conformance module, by Word and
Excel (opt-in, `FSAGEN_OFFICE=1`: both open every kind with macros forcibly
disabled and find the project; Word compiles the source and saves it back
unchanged), and by olevba where it is installed (it extracts each macro and
reports only its entry point; on Excel projects it also reports the class
GUIDs every Excel project carries as hex strings, as it does for a workbook
Excel wrote).

**Deviations from the plan.** Spreadsheets get an `xlsx` block of their own
rather than sharing `docx`. The PROJECT stream's encrypted fields, the module
list and the dir stream were checked against a project Excel wrote
(XlsxWriter's sample), which is how the project-key rule (the byte sum of the
project's ID, braces included) was confirmed before Word confirmed the whole.

### Hard links, symlinks and junctions

Three new actions make links, and fsagen never follows one. `hardlink` gives a
file a second name; `symlink` writes a target relative to the link's directory
(dangling allowed; outside the output only with `allow_external_target`), its
`target_type` deciding on Windows whether it is a directory link;
`junction` (Windows) points at a directory in the output.

The model gained a layer of names: an object has one or more, each with its
own `$FILE_NAME` times, ids tag names rather than objects, and deleting a name
the file is not left without only unlinks it. Nothing is written, read,
copied or streamed through a link, and every walk of the output stops at one:
SHA256SUMS lists a hard-linked file under each name and counts links in
`outputs.links` instead of reading them; the observed timeline types a
junction as a link from its reparse tag rather than as an irregular file; the
golden fingerprint writes `l <target> <path>`; `--into-existing` seeds links
and hard-linked names as such. On Unix times are now set with
`AT_SYMLINK_NOFOLLOW` (`os.Root.Chtimes` followed a final symlink), so a
link's times are its own.

On Windows the symlink and junction reparse points are written by fsagen,
relative to their parent opened through the root, laid out as
`CreateSymbolicLinkW` and `mklink /J` lay them out; the junction's data
matches `mklink /J`'s byte for byte. Symlinks need Developer Mode or the
privilege, which is tried once in a temporary directory. Loops of every kind
are written and every walk ends. All of it runs on Windows 11 and on Linux
(ext4).

The ledger's `kind` adds `symlink` and `junction`, with `target`, and `links`
counts a hard-linked file's names; the answer key adds `linked`, `unlinked`,
and `created` with a link's `target`; timelines name a link `path -> target`
and give `links` and `link_target` in JSON lines.

**Deviations from the plan.** A link the platform cannot make is a pre-flight
error even with `--on-unsupported=skip`: later actions and the settle pass
would act on a name that is not there. A junction's target is a path in the
output, written as `path` is, while a symlink's is relative to the link, as
the file system stores it. Directory descent is not guarded by a set of
visited file IDs: no walk descends through a link in the first place, which
the loop test proves.

### Generator version 7

`constant.GeneratorVersion` is **7**, the single bump this release planned. It
bundles three changes to covered output:

- **Bulk mode gains the forensic artefacts**: a shortcut, a prefetch file named
  for its program and path hash, an event log, `NTUSER.DAT` (in a profile
  directory), `wtmp` and `audit.log` (in a host directory), and a `.docm` and
  `.xlsm` with an inert macro, each from the builder its format uses
  (`TestBulkForensicKindsParse`). Files are still rendered in parallel but are
  now written in the plan's order, so a target that places every byte itself
  gets the same order every run.
- **The answer key gives each `created` and `modified` fact its `md5`**, as
  timelines and most tools report it beside the SHA-256.
- **The run manifest records more of what the target can do**: `slack` and
  `cluster_size`, `hardlinks`, `symlinks` and `junctions`, and
  `filename_times_controlled` from the target rather than as a constant.

A new example, `playbook-macro-phish`, puts a `.docm`, a `timestomp`, a
`hardlink` and an `.xlsx` through every golden and the determinism harness;
it uses no feature a platform lacks, so it runs everywhere. Its
`mtime_before_crtime` fact names the payload by its first name, not the hard
link that sorts before it.

The goldens were recorded under `testdata/golden/v7/` on Windows 11 and under
WSL Ubuntu, and each platform then reproduced them without `-update`. Against
v6, on both platforms, every example's corpus fingerprint, ledger, modelled
bodyfile and dry-run listing is byte-identical; every answer key differs only
by the new `md5` fields; and the two bulk corpora differ only by the files of
the new kinds, every existing bulk file keeping its name and bytes.

### Scoring a tool: `fsagen diff-oracle`

fsagen's first subcommand scores what a forensic tool reports about a
generated tree against what the run made, in six categories: the names
present, the deleted entries, the named streams, the times of everything
found, the digests the tool computed, and links. Each gets true and false
positives and negatives, precision, recall and F1, with the tool's line numbers
for everything missed, made up or wrong; `--scorecard` writes the lot as JSON
and `--fail-under` turns the overall F1 into an exit status (3). It reads The
Sleuth Kit's bodyfile (`fls -m`), Plaso's l2tcsv, dynamic CSV and JSON lines,
and fsagen's own timelines, detecting which from the first line, and finds the
output root inside the tool's paths itself. `run` dispatches to it when the
first argument is `diff-oracle`, so a directory of that name is written
`./diff-oracle` (`TestDiffOracleDispatch`). New package `oracle/`; no new
dependency.

Deviations from the plan:

- **The expected state is folded from the ledger, not the answer key.** The
  answer key is derived from the ledger and leaves out what scoring needs most:
  the times of every object, directories and the deleted. `SHA256SUMS`,
  written beside it, covers the files no operation made, so the oracle also
  scores `--into-existing` runs and bulk corpora (names and digests).
- **Directory times need `--model`.** Every entry added to a directory moves its
  times at the operation's clock, which the ledger does not record (a playbook's
  jitter, a manifest's explicit times); so does a file's change time after a
  `rotate` or the loss of one of its hard links. Those are left unscored
  rather than guessed, unless a modelled timeline of the run supplies them. The
  plan had `--model` supply inodes; inodes are instead checked for consistency
  (a hard-linked file's names share one), which needs no model.
- **NTFS `$FILE_NAME` records, residue and slack are not scored yet.** They are
  recognised and set aside; the image targets, where fsagen controls them,
  will score them.
- **Plaso was not run.** WSL has neither Python's headers nor a password-free
  sudo to build it. The readers follow Plaso's output modules as its source
  writes them (17 unquoted l2tcsv fields with commas written as spaces, MACB
  grouping per instant, `TYPE:` display-name prefixes, the `fs:stat` formatter's
  message), and the fixtures were written to that shape from the macro-phish
  example's model.

Checked by `TestModelledBodyfilesScoreOne`: every example's modelled bodyfile,
on both platforms, scores 1 in every category against its ledger with no
tolerance, which is the proof that the ledger fold reproduces the model,
deleted generations, hard links, streams and stomped times included. A real
run's modelled timeline also scores 1 with directory times
(`TestDiffOracleScoresFsagenTimelines`), and so does its observed timeline read
back from this NTFS volume, on everything a live volume keeps.

The README's quick start said fifteen worked examples; there are sixteen since
`playbook-macro-phish`.

### Targets: one interface for a live directory and an image

Everything a run writes and reads back now goes through the new leaf package
`target/`, so the file-system images to come can take a scenario without the
executor knowing which it has. It holds the shared types (`Times`,
`Granularity`, `Meta`, `Stream`, `Caps`, `SlackSupport`, `File`), the
`Reader`, `Writer` and `Target` interfaces, and three optional ones a target
implements when its capabilities say so: `Linker`, `Slacker`, and `Finisher`,
for a target built in one go whose output is final only once `Finish` has run.
No output changed: every golden, on both platforms, is byte-identical.

- `sandbox.FS` is the live target. Its types are aliases of `target`'s, and the
  capability set moved from `manifest.Caps` to `FS.Caps`; `compile.Caps` and
  `compile.SlackSupport` are aliases too.
- `manifest.ExecContext.FS` is a `target.Target`, with a `Read` reader that
  verifying reads back through. `manifest.Run` executes a compiled program on
  any target; `manifest.Finish` settles and verifies, and for a `Finisher`
  settles, finishes, and then verifies through the finished reader. The CLI's
  generating pass keeps its live order (digest, then settle, which puts back
  any access time the digests moved) and takes the other for a `Finisher`
  (settle, finish, verify, then digest what was finished).
- `runinfo.WriteSums`, `libgen.Generate`, `timeline.GenerateFrom` (new; a
  timeline of any `target.Reader`) and `--into-existing`'s model seeding take
  the interfaces. `SHA256SUMS` is now read through the quiet handles every
  other read uses; its bytes are the same.
- `internal/memtarget` is a target in memory, and a `Finisher`.
  `TestOneGoTargetReproducesWindowsGoldens` runs every example through the
  CLI's generating pass into it with the capabilities of a Windows NTFS volume:
  the corpus, ledger, answer key and `SHA256SUMS` are the Windows goldens', on
  any platform, with `Finish` called once and nothing written after it
  (truncating its streams, or dropping change times from its reads, fails the
  test). `TestOneGoTargetTakesBulk` does the same for the bulk golden.

Deviations from the plan:

- **The residue and slack records, `$FILE_NAME` times and the image clock wait
  for the first image.** The plan had their types (`Forensic`,
  `FilenameTimer`, `OpObserver`) land here; nothing would use them yet, and
  the first driver that produces them should set their shape.
- **`--validate` and `--dry-run` still take the host's capabilities;** they take
  an image driver's with `--image`, which arrives with the first image.
- **An observed timeline still reports permission bits the host's way**
  (`sandbox.ModeHasPermissions`); a target-owned answer comes with the first
  image reader, which is when an observed timeline of an image is allowed.

`TestCFBReadByWindows` failed now and then with a nil COM interface: the address
of a local passed through the test's `comCall` helper as a `uintptr` could go
stale when the stack grew before the call. The helper is now marked
`//go:uintptrescapes`, as `syscall.SyscallN` and x/sys's `LazyProc.Call` are.

### FAT32 disk images

`--image FILE --image-fs fat32 --image-size SIZE` writes a scenario into a disk
image that fsagen builds byte by byte, in place of an output directory (see
_Disk images_ in the README). The same seed and input make the same image on
every platform.

**The image.**
- **Containers** (`volume/container`): a raw disk (`.raw`, `.dd`, `.img`) or
  a fixed VHD (`.vhd`). The file system is bare (`--partition none`) or in
  one MBR partition 1 MiB in (`--partition mbr`, the default). The disk
  signature, VHD ID and volume serial are drawn from the seed, on a key no
  content draws from.
- **FAT32** (`volume/fat`), laid out as Windows formats and writes it:
  - Windows' cluster sizes, and Microsoft's formula for the FAT size. Fewer
    than 65,525 clusters is refused, with the smallest size that would do.
  - Long names, with the short names Windows generates, the `~5`-on checksum
    form included. It was checked against names Windows 11 made itself,
    since the checksum ReactOS publishes does not match them.
  - NTRes case bits for 8.3 names whose parts are each one case.
  - Times in UTC, to FAT's resolution.
  - Deleted entries reused first; `0xE5` deletes that leave the entry and
    the clusters.
  - Renames that leave their old entries; truncated rewrites that leave
    their old clusters.
  - Next-fit allocation, as Windows does, or `--alloc first-fit`.
- **Writing and failure.** The image is written to a temporary file and named
  only once the run succeeds. A failed run leaves nothing but its records,
  and an image already there is replaced only with `--clean`.
- **Checking first.** `--validate` and `--dry-run` with `--image` check the
  scenario against the image's file system, not the host's.

**What is refused.** Pre-flight now also refuses:
- a time outside what the volume can store: `Caps.MinTime` and `MaxTime`, so
  for FAT nothing before 1980 or after 2107;
- a name the volume cannot hold: `Caps.ValidName`, for FAT the characters
  Windows forbids;
- two names that differ only in case, on a volume that cannot tell them
  apart (`Caps.FoldsCase`), even with `--allow-nonportable`.

On every target, a slack block's `cluster_size` must now be the volume's
whenever the volume's is known. Before, that applied to live NTFS only.

**What the run records.**
- **Run manifest.** It gains `"target": "image"`, an `image` block, `image_sha256`
  under `outputs`, and `capabilities.time_resolution`: how finely the volume
  keeps each time. All of these are left out for a run into a directory.
- **Answer key.** It gains `residue` facts: the deleted entry each delete or
  rename left, by its Sleuth Kit address and image offset, and whether a
  later name reused it; the extents and digest of what a delete or overwrite
  freed; and whether that content is still `full`y, `partial`ly or not at
  all recoverable, with the ranges overwritten.
- **Slack.** Slack on an image is written into the cluster and recorded
  `verified: true`.

**diff-oracle on image runs.**
- It allows for the volume's resolution: FAT keeps the access date only, so a
  report of midnight matches.
- It matches a deleted entry by the address the answer key gives it. FAT
  loses a deleted name's first character, which is how The Sleuth Kit shows
  it.
- It does not expect an entry a later write reused.

TSK's bodyfile of the fixture image scores 1.0 for files, deleted entries and
times.

**Core.** `volume.Volume` is the target an image is written through. It keeps
the tree as the scenario sees it and hands each change to a `volume.Driver`,
which writes content and directories through to the image as they change and
the FATs and boot sectors when finished. Once finished, the driver reads the
image back with its own parser. That parser is what the run verifies and
digests, and what an observed timeline of an image reads (`--timeline` works
with `--image`). Residue is recorded as it is left (`volume.Tracker`), and
whether it survived is worked out once the image is finished.

**Interfaces.** `target` gains:
- `OpObserver`, whose `BeginOp(n)` the executor calls before each operation,
  so residue names the ledger entry that left it;
- `Forensic`, for a target that reports `Residue()`;
- the `Residue`, `ResidueEntry` and `Extent` records.

**Tests.**
- **Every example.** `TestImagesTakeEveryExample` writes every example FAT can
  hold into an image. Its `SHA256SUMS` and ledger match the same run in
  memory. The example with a hard link is refused.
- **Pinned image.** `TestImageGolden` pins the image, residue and sums of
  `testdata/image/fat32.yaml`, the same on Windows and Linux.
  `TestImageTakesBulk` puts the bulk golden in an image.
- **Third-party readers.**
  - `TestFAT32ReadByGoDiskfs`, in the conformance module (go-diskfs, MIT, a
    test-only dependency there).
  - `TestImageReadBy7Zip`.
  - `TestImageCheckedByFsckVfat`.
  - `TestImageListedByTSK`, which also scores TSK with `--fail-under 1`.

  The three tool tests skip where the tool is absent. All four ran: 7-Zip on
  Windows 11; dosfstools 4.2 and The Sleuth Kit 4.12.1 in WSL Ubuntu 24.04,
  unpacked from their packages without installing them.
- **Driver and core.** Unit tests cover the driver's names, deletes, entry
  reuse, allocation policies, overwrites, directory growth, times, slack and
  renames. They also cover the allocator and the MBR, VHD geometry and VHD
  footer.

Deviations from the plan:

- **A smaller driver interface.** It has no `Plan`, `OnResize` or `Fold`
  hooks. Content is committed when a handle closes, and a name's validity
  and case folding are capabilities pre-flight checks. Links and streams
  get hooks when a driver needs them.
- **No image clock in `OpObserver`.** The executor stamps every object's
  times after each operation, so the driver's clock is only the image time,
  for what exists before the scenario stamps it.
- **`volume/image`** is a new package. It puts a driver and a container
  together for the command, and lays an image out for `--validate`.
- **The oracle's image scoring is pulled forward** from the NTFS landing, in
  part. Deleted entries are matched by address, but residue and slack are
  not yet categories of their own.
- **Choices made without a FAT volume to compare against.** Mounting one on
  Windows needs an administrator, so these follow what is known of Windows'
  FAT driver:
  - an 8.3 name with mixed case gets a long name and its upper-cased short
    name;
  - a rename writes the new entries before deleting the old;
  - a truncated rewrite takes new clusters;
  - a deleted entry keeps the high word of its start cluster.

  Short names skip characters outside ASCII, as Windows' NTFS short names
  do; Windows' FAT driver may map some through the OEM code page.
- **Not yet run:** Windows mounting the VHD and `chkdsk` on it (both need an
  administrator), and the Fedora VM. Its tools ran in WSL instead.

### ext4 disk images

`--image-fs ext4` writes a scenario into an ext4 volume that fsagen builds byte
by byte (`volume/ext4`), in the same raw or VHD containers as FAT32, with
type `0x83` in the MBR. See _Disk images_ in the README.

**Format, as mke2fs makes it.**
- The empty volume is mke2fs 1.47's byte for byte, checksums included, when
  mke2fs is given the same UUID, hash seed and time. `TestFormatMatchesMke2fs`
  compares nine geometries: 1, 2 and 4 KiB blocks, from one group to eighteen,
  and two and three flex groups.
- The geometry is mke2fs's for the size:
  - its inode ratio and 5% reserved blocks;
  - a last group too small for its bookkeeping dropped;
  - sparse superblock and descriptor backups;
  - each flex group's bitmaps and inode tables placed as
    `ext2fs_allocate_group_table` places them;
  - unused groups left uninitialised;
  - lost+found grown to 16 KiB.
- The features are `filetype`, `extent`, `flex_bg`, `sparse_super`,
  `large_file`, `dir_nlink`, `extra_isize` and `metadata_csum`. That is
  mke2fs's ext4 set less the journal, `64bit`, `resize_inode`, `dir_index`,
  `huge_file` and `ext_attr`.
- The UUID, hash seed and inode generations are drawn from the seed, on the
  image's key.

**Writes, as Linux makes them.**
- All four times to the nanosecond, with the epoch bits that carry them past
  2038; the change time and creation time are the scenario's.
- Hard links, and symlinks: in the inode up to 59 bytes, else in a block.
- Extent trees in the inode, or in leaf blocks it indexes when a file needs
  more than four extents.
- Linear directories: a new name goes in the first entry with room, which it
  splits.
- New inodes from the parent's flex group. One deleted less than a minute
  before is skipped while there is another, as Linux does with no journal.
- A delete does what Linux has done since 5.14:
  - the entry is wiped, folded into the one before it;
  - the inode keeps its mode and times and gains a deletion time, which is
    also its change time;
  - its size, links, blocks count and extents' starts and lengths are
    zeroed;
  - its blocks are freed with their bytes in place.

**What is refused.** Pre-flight refuses streams, junctions, a time outside
1901 to 2446, a name over 255 bytes, and `lost+found` at the root. That last
uses a new `Caps.Reserved`.

**Records.**
- The run manifest's image block gives `uuid` in place of `serial`, which is
  now left out where it does not apply.
- Residue entries are `ext4_inode`, numbered as The Sleuth Kit numbers inodes,
  with `deleted`: the time of the delete.
- diff-oracle takes a deleted inode's change time from that.
- Time resolution is a nanosecond for all four times.

**Interfaces.**
- `target.OpObserver.BeginOp` now also takes the operation's time, which a
  driver that stamps times itself (`volume.Clocked`) is given.
- `volume.Volume` makes hard links and symlinks, through a driver's
  `volume.LinkDriver` and `Create`. Like the sandbox, it makes a link's
  missing parent directories.

**Tests.**
- `TestExt4ImageGolden` pins `testdata/image/ext4.yaml`'s image, residue and
  sums.
- `TestImagesTakeEveryExample` runs every example through both file systems,
  and on ext4 the hard-link example is taken. `TestImageTakesBulk` does the
  same for the bulk corpus.
- `TestExt4ObservedTimelineToTheNanosecond` scores fsagen's own reading of the
  image at 1.0 with no tolerance.
- Third-party readers, in the conformance module:
  - `TestExt4ReadByGoDiskfs`: go-diskfs reads every name, byte, link target,
    inode and link count back, checking checksums as it goes.
  - `TestExt4ReadByGoExt4`: go-ext4 (MIT, a test-only dependency there) does
    the same. It refuses symlinks short enough to live in the inode, so
    those are checked by their entries.
- External tools, opt-in:
  - `TestExt4CheckedByE2fsck`. `e2fsck -fn` also checks every volume the
    driver's unit tests make, wherever e2fsprogs is installed.
  - `TestExt4ListedByTSK` finds every deleted inode as an orphan, and scores
    TSK's bodyfile with `--fail-under 1`.
- All of them ran in WSL Ubuntu 24.04, with e2fsprogs 1.47.0 and The Sleuth
  Kit 4.12.1.

Deviations from the plan:

- **`flex_bg` and `metadata_csum` are in from the start.** The plan put them
  in a follow-up. Neither Go reader reads ext4 without them: go-diskfs
  v1.9.3 checks inode checksums whatever the features say, and go-ext4
  requires `flex_bg`. Both are also what mke2fs makes by default.
- **The plan said a deleted name's bytes stay behind.** Since Linux 5.14,
  `ext4_generic_delete_entry` zeroes the entry, so nothing of the name is
  left, and fsagen does the same. The deleted inode is what remains, and The
  Sleuth Kit lists it as an orphan.
- **The Sleuth Kit 4.12.1 lists no orphan at all on a volume where a
  directory was deleted.** It fails to open the emptied directory inode while
  looking for orphans. The ext4 fixture therefore deletes no directory; the
  driver's tests do.
- **An image now has a clock.** M4.2.1 gave `OpObserver` none. ext4 stamps
  deletions and changes itself, so the executor passes each operation's time.
- **Placement is not Linux's.** Blocks come from fsagen's allocator (next-fit
  or first-fit), not mballoc. Directories get inodes as files do, not
  through Orlov.
- **A rename onto an existing name** removes that name, then adds the new
  one. Linux reuses the entry in place.

### NTFS disk images

`--image-fs ntfs` writes a scenario into an NTFS volume that fsagen builds byte
by byte (`volume/ntfs`), in the same raw or VHD containers, with type `0x07` in
the MBR. This is the first of the plan's three NTFS landings (M4.2.3a). See
_Disk images_ in the README.

**Format, as mkntfs makes it.**
- The empty volume is mkntfs 2022.10.3's byte for byte, given the same serial
  number, partition start and time (its `-T`). `TestFormatMatchesMkntfs`
  compares nine geometries, 3 to 64 MiB, with 512-byte to 64 KiB clusters and
  a label. Two things are masked:
  - the boot code, which fsagen does not write;
  - the padding of attributes and index entries, which mkntfs leaves holding
    whatever its buffers held.
- The geometry and placement are mkntfs's:
  - `$MFT` at 16 KiB after its bitmap;
  - `$MFTMirr` and `$LogFile` in the middle of the volume, the log sized for
    the volume and filled with `0xFF`;
  - the root's descriptor and index block, `$AttrDef`, `$Bitmap`, `$SDS` and
    `$UpCase` from the end of the MFT zone;
  - records 0 to 26 with their attributes, instance numbers and descriptors.
- `$UpCase` is the table Windows 8 and later write (the one mkntfs writes; its
  MD5 is the Windows 8 one ntfs-3g records), kept as 134 runs, with its CRC-64
  in `$UpCase:$Info`. `$AttrDef` is Windows' table.
- The 64-bit serial is drawn from the seed, on the image's key. FAT32's 32-bit
  serial is drawn as before, so no FAT32 image changes.

**Writes, as Windows makes them.**
- A record from 64 up for each new object, with a 72-byte
  `$STANDARD_INFORMATION`, a `$FILE_NAME` in the Win32 namespace (Win32 and DOS
  for a valid upper-case 8.3 name) and `$DATA` or `$INDEX_ROOT`.
- Two security descriptors are added to `$Secure` the first time they are
  needed, a file's and a directory's: owned by the Administrators, with the ACEs
  they inherit from the root, filed in `$SDS` twice 256 KiB apart, in `$SDH`
  by hash and in `$SII` by ID.
- Content in the record while it fits, then in clusters for good; a truncated
  rewrite takes new clusters; the last cluster is zeroed past the end.
- `$MFT` grows a record at a time, its clusters 16 records at a time after its
  last one, and `$MFTMirr` follows its first records.
- A directory's entries in `$INDEX_ROOT` until the record is full, then all in
  one index block, with `$BITMAP` and `$INDEX_ALLOCATION`.
- All four times to 100 ns; `$FILE_NAME`'s times at birth and on a rename, as
  the model has them.
- Every record and index block written with the next update sequence number.
- A delete clears the record's in-use flag and moves its sequence number on,
  and leaves its attributes; frees its clusters with their bytes; and takes
  its entry out of the index, the entries after it moving up and leaving their
  old bytes past the end.
- A mode without the owner's write bit sets the read-only attribute, as Go's
  `os.Chmod` does on Windows.

**What is refused.** Pre-flight refuses streams, links, junctions, slack, a
timestomp's `$FILE_NAME` times, a time before 1601, a name Windows forbids, and
NTFS's own names at the root in any case. `Caps.Reserved` is now matched
without regard to case on a volume that folds case. The slack refusal now says
which images keep slack.

**Records.**
- The run manifest's image block gives the 64-bit `serial` as 16 hex digits.
- Residue entries are `ntfs_mft_record`, numbered as The Sleuth Kit numbers
  records, with `seq`: the sequence number the delete left.
- Time resolution is 100 ns for all four times.

**Tests.**
- `TestNTFSImageGolden` pins `testdata/image/ntfs.yaml`'s image, residue and
  sums, the same on Windows and Linux.
- `TestNTFSObservedTimelineTo100ns` scores fsagen's own reading of the image at
  1.0 with no tolerance.
- `TestNTFSRefusesWhatItCannotHold` covers the refusals above.
- `TestImagesTakeEveryExample` and `TestImageTakesBulk` run NTFS too.
- The driver's own tests cover the plan's geometry, `$Secure`, resident and
  non-resident content, the delete, record reuse, `$MFT`'s growth, the move to
  an index block, the rename and names. Where The Sleuth Kit and ntfs-3g are
  installed, `fls` and `ntfsls` read every volume they make.
- Five deliberate breakages were each caught by those tests and the golden:
  keeping the in-use flag, keeping the sequence number, writing the index
  block from zeros (no slack), not rewriting `$FILE_NAME` on a rename, and
  freeing no clusters.
- Third-party readers:
  - `TestNTFSReadByGoNTFS` (conformance module): go-ntfs walks the indexes and
    reads every name, byte, record number, link count and time back, bare and
    in a VHD, and each deleted record with its sequence number and name. A
    one-tick shift in how times are written and read, which fsagen's own
    reader agreed with, was caught by it.
  - `TestImageReadBy7Zip` now extracts the NTFS fixture too.
  - `TestNTFSListedByTSK` finds every file and every deleted record under its
    name, and scores TSK's bodyfile with `--fail-under 1`.
- All of them ran in WSL Ubuntu 24.04, with ntfs-3g 2022.10.3 and The Sleuth
  Kit 4.12.1; `ntfsinfo` and `ntfsfix -n` accept the fixture's image too.

Deviations from the plan:

- **Directories hold one index block, not none.** The plan's flat volume would
  keep every directory in its `$INDEX_ROOT`, but mkntfs's root already lives
  in an index block, so this landing writes one. Splitting it, for a directory
  bigger than one 4 KiB block, is M4.2.3b. Until then such a directory stops
  the run when it fills, and no image is written; three examples do that.
- **No boot code.** mkntfs's is GPL; fsagen writes none, so Windows cannot boot
  from the volume, which it could not anyway.
- **Records count from 64, and `$MFT` grows 16 records at a time,** as
  libntfs-3g does. Where Windows puts records and grows `$MFT` cannot be read
  without an administrator.
- **No log.** `$LogFile` stays as mkntfs left it and every log sequence number
  is 0. Windows starts the log afresh when it mounts such a volume.
- **The residue of a delete is the record and its clusters.** The index entry's
  old bytes are left as index slack, as the plan says, and tested, but they are
  not a residue fact: entries move up over a removed one, so what is left is
  not the removed entry's bytes at a fixed place. A rename records no residue.
- **`$FILE_NAME` sizes follow the content,** in the record and the index alike.
  Windows updates only the index's copy, and lazily.
- **Not checked against Windows itself.** chkdsk and mounting the image need an
  administrator, and ntfs-3g's `ntfssecaudit` needs root; neither is available
  here. Which names Windows files in the Win32 and DOS namespace with short
  names off is taken from its documented behaviour, not observed.

## v0.2.0 — the bulk corpus becomes answerable for itself (2026-10-02)

Generator version **6**, and the first tagged release whose output differs from
its predecessor's. The bulk generator hand-built its own email and its own PDF
instead of using the builders the rest of fsagen uses, and it was the one part of
the tool with no recorded bytes behind it — so what it wrote was wrong in small
ways *and* unguarded. Both are fixed here.

Nothing a manifest or a playbook writes changes. Of the 135 golden files recorded
for v0.1.0, 129 are byte-identical under this generator. The other six are
fingerprint fixtures whose lines were **reordered** by a fix to the test
harness's own sort key; the bytes they describe are unchanged. So only bulk mode
writes different bytes, and only for three of its twenty-one kinds — `.eml`,
`.mbox` and `.pdf`. A corpus you compare against needs regenerating only if it
came from `--bulk`.


### The bulk eml, mbox and pdf come from the real builders (e5dd74f)

The bulk corpus wrote its own email and its own PDF. `genEml` and `genMbox`
assembled RFC 5322 with `fmt.Sprintf`; `genMbox` dated its `From ` separator in
RFC 5322 form rather than ctime, and never escaped a body line beginning
`From `, which is how one message comes to be read as two. `genPdf` hand-rolled
gofpdf beside `RenderPDF`, never checked `pdf.Err()`, and placed its 25 lines at
fixed coordinates starting at y=0 — above the top of the page, so the first line
was invisible. All three now go through `email.Build`, `email.ToMbox` and
`RenderPDF`, the same builders the `email` action and the `pdf` format use, so a
generated message carries canonical folded headers and a Message-ID and a
generated PDF is paginated with margins.

That changes generated bytes, so `constant.GeneratorVersion` is **6** and the
goldens are re-recorded under `testdata/golden/v6/`. All 135 of them are
byte-identical to v5's, because no example uses bulk mode: the bulk corpus — the
largest thing fsagen writes — has no golden coverage at all, and nothing in the
suite would have caught this change.
`TestBulkEmailAndPdfComeFromTheSharedBuilders` now covers the three generators,
which had no test between them. `testdata/golden/v5/` is no longer read by any
test; removing it is the owner's call.

The three "50 timestamped lines" loops behind `log`, `jsonl` and `syslog` are one
`timestampedLines` helper. That part is byte-identical, which was checked by
running the goldens against it before the version moved rather than asserted
afterwards. `genLog` draws its event before its user, which is not the order the
two are printed in, so the draws stay where they were and a comment says why.
The email format switch in `manifest` compares against `spec.FormatEML` and
`spec.FormatMbox` rather than the bare strings it had been left with.

Verified on both platforms: vet, gofmt, `go mod tidy -diff`, the eight
cross-compiled builds and `go test -race ./...` on Windows 11, and the same on
Ubuntu 24.04/ext4 under WSL2 — where the race detector had never run before,
every earlier Linux run having used a `CGO_ENABLED=0` cross-build. 30 golden
subtests and 0 skips on each. `./build.sh` also ran end-to-end on a Linux host
for the first time: 6/6 targets, checksums written, and its smoke test reports
`generator version 6`.

### A typed action and format vocabulary, and the last of the polish (5e9dbb3)

Actions and formats were bare strings in about 250 places across eight packages,
and nothing but a test tied the dispatch tables to the closed set. `spec` now
declares `ActionName` and `Format` with a constant per value, and
`spec.Operation` carries those types: `compile.Fields`, `Required`, `Formats`,
the simulator table, the executor table and the answer key are all keyed off
them, so renaming an action is a compile error at every mention rather than a
value nothing matches at run time, and an action can no longer be passed where a
format is wanted. `spec.Actions` replaces `compile.Actions`, beside the
constants it holds. The published JSON Schema, the ledger, the dry-run listing
and all 135 goldens are byte-identical: a named string type marshals as its
string.

The binary writers were four near-identical families, two of which (`put32` and
`putBE32`) differed by three characters for opposite byte orders. Every one is
gone: PE, MP4 and PNG append through `encoding/binary` with the order named at
the call site, and the zip headers keep one buffer pair, now called `putLE16`
and `putLE32`. `BuildZip` was the longest function in the repo and is now
eighteen lines, with each member's header fields worked out once and written
twice from one struct rather than twice from scratch.

Smaller things, each a place where two copies could drift or a number meant
something it did not say: `timeline.Formats` is derived from the writers table
it claimed to be derived from; `Sources.ReadFile` and `Check` share one
path-resolving step instead of two copies of it and of a 100-character error
string; `compile.Load` releases the source root on one deferred path rather than
seven; the settle pause goes through an injected clock, so the retry test
asserts which pauses were taken without taking them; the Windows NT opens share
one `ntOpen`, and the suspend-access-time sentinel is named once; `100` is
`tick`, `1e7` is `ticksPerSecond`, and `1<<48-1` is `mftRecordMask`; the
platform's permission-bit question moved to `sandbox`, where the other platform
answers live; `contains` is `slices.Contains`; and `main` uses
`sandbox.FileMode`/`DirMode` rather than raw octal. `schema.nestedDefs` gained
the covering test it never had, which catches a refinement naming a field the
struct does not have — the silent half of the mistake its type assertions used
to make loudly.

### The release scripts take the version, and strip what they build (5e9dbb3, bd5e22c)

`./build.sh v0.1.0` and `.\build.ps1 v0.1.0` build that version: it names every
asset and is stamped into the binaries with `-ldflags -X`, so `fsagen --version`
reports the release rather than the pseudo-version Go derives from an untagged
commit. That is what the v0.1.0 assets shipped with — built before the tag
existed, they are named `fsagen_6b5b91a_*` and report
`v0.0.0-20260927132346-6b5b91ad4367`. Each script now runs the host binary after
building and fails if it does not report the version in its own filename, which
also catches a `-X` that quietly hit nothing because the variable moved.

The version stays optional and still defaults to `git describe`, because that is
what a test build wants; the difference is that the default is stamped too, so
the filename and `--version` agree either way. The scripts also say when the
commit being built carries no tag, carries a different one, or has uncommitted
changes. `runinfo.Build` prefers the stamped version and takes the revision from
the toolchain regardless, so the commit behind a binary stays checkable against
the tag whatever the version claims. Both scripts still write byte-identical
checksums for the same version and toolchain, checked across the two.

What they build is now a release build. `-s -w` drop the symbol table and the
DWARF data, on top of the `-trimpath` that was already there, which takes the
six assets from 85 MiB to 54. Nothing diagnostic goes with them: a panic still
names its functions, files and lines, because those come from the pclntab rather
than from either section stripped — so do not put the symbols back thinking a
crash report would otherwise be unreadable. Nothing generated moves either; the
same playbook run through a stripped and an unstripped binary writes the same
287 digests. Go has no optimisation level to raise — it always optimises unless
`-gcflags all=-N -l` asks it not to — so stripping is the whole of what a
release build means here. The published checksums change with it, which is
checked across both scripts as before.

### The bulk corpus is pinned by a golden (b5ecf68)

Generator version 6 changed the bytes of the bulk `.eml`, `.mbox` and `.pdf` and
moved not one of the 135 golden files, because every shipped example is a
manifest or a playbook. Nothing recorded covered `--bulk` at all, so a change to
any of the twenty-one generators behind it could alter the largest output fsagen
writes while the whole suite stayed green. That is the one gap this pass found
that was not in the original plan, and `TestBulkGoldens` closes it.

Two corpora are pinned by fingerprint: `one-of-each` (seed 7, one directory, one
file of every kind — short enough to read, and it lists all twenty-one) and
`two-levels` (seed 7, limit 2, depth 2 — repeats a kind within a directory and
nests, which is what exercises the deterministic name-retry in `Plan`). Both are
platform-independent and live beside the dry-run goldens rather than under an OS
directory: a fingerprint records names, sizes and digests but never times, and a
bulk file's bytes come from the seed and the start time alone. Recorded on
Windows, they pass unchanged on Ubuntu 24.04/ext4.

The guard was checked rather than assumed. Changing `genMarkdown`'s heading from
`#` to `##` — one character in one of the twenty-one — fails both subtests,
names the `.md` file in each corpus, and says to bump `constant.GeneratorVersion`
rather than edit the fixture. The input hash for a corpus is the seed and shape
rather than a file, through a new `testutil.SpecHash`, so changing what is
generated re-records the golden while the same request producing different bytes
stays a hard failure.

The documented golden invariant is unchanged at **30 subtests, 0 skips** for
`TestExampleContentGoldens|TestDryRunGoldens`; the bulk goldens are 2 more
subtests on top, and the tree holds 137 files. README now says which golden
directories are platform-independent and which are not, and `docs/testing.md`
records that F-DET-1 is covered twice over: `TestBulkDeterministic` for a corpus
stable within a run, `TestBulkGoldens` for it being the recorded one.

### The golden harness sorts by path (b5ecf68)

`testutil.Fingerprint` describes a tree one line per entry and sorts them, and
every golden claim in the suite rests on that order being a property of the tree
rather than of the run. For a path containing a space it was neither. The sort
key was recovered from the finished line as its last space-delimited token, so
`Users/User1/AppData/Local/Google/Chrome/User Data/Default/History` sorted under
`Data/Default/History` — above the `Users/` directory that contains it — and two
paths whose last segments matched compared equal under a `sort.Slice` that is
not stable, leaving their order to the sort.

The key is now carried from the path the line was built from, the way
`runinfo.Sums` has always carried it in a `sumLine` field rather than parsing it
back out. It keeps the shape it had — a directory's trailing slash and a
stream's `:<stream>` suffix are part of it — so the fix reorders only the lines
it actually affected, and equal keys fall back to the whole line, which makes the
order total rather than merely stable.

Six fixtures moved: `playbook-browsing`, `playbook-comprehensive-ransomware` and
`playbook-malware-lifecycle`, under both `windows/` and `linux/`, by 3, 4 and 4
lines each — exactly the number of space-containing paths in each. Every
re-record was checked to be a permutation, the sorted set of lines hashing
identically before and after, so no digest, size or name changed anywhere and
`constant.GeneratorVersion` stays **6**. This is the harness's recording order,
not anything fsagen writes.

Re-recording meant deleting those six first, because `CheckGolden` refuses to
rewrite a golden whose input hash is unchanged even with `-update` — the guard
that makes a moved byte a hard failure rather than a fixture edit. That cost is
why this was left alone at v0.1.0, listed there as one of two known problems kept
on purpose. The other, the silent capability downgrade in `sandbox.probeVolume`,
still stands: failing the run instead could break real use on a network share,
and it cannot be tested here.

`internal/testutil` had no test of its own and now has one.
`TestFingerprintSortsByPath` builds a tree holding both halves of the flaw —
`a b/c`, which sorted after `a/b`, and `p q/same` beside `r q/same`, which
compared equal — and pins the whole order. Reverting the key to the old
last-token form fails it on both counts.

### A readability and correctness pass (bcd403d)

Every function is now within two levels of nesting. The five largest bodies
broke into named phases — `BuildPE` 222 lines to 9, `compilePlaybook` 264 to 26,
`apply` 229 to 13, `generate` 220 to 75, `executeOp` 130 to 7 — and the three
switches over `op.Action` became dispatch tables with tests proving they agree
with `compile.Actions`, which nothing had checked before. `spec.Action` embeds
`spec.Operation` instead of restating all 32 of its fields, so adding a field is
one edit rather than five. One `reporter` type replaced eight copies of the same
error-positioning closure. Two dead exported vars are gone, five more symbols no
longer cross a package boundary, and the two package-level test hooks
(`capsOverride`, `afterSettle`) are injected, so those tests can run in parallel.

Reshaping the code surfaced real defects, each fixed here:

- **The extension safety net was bypassed for `ref:` targets.** `path.Ext` read
  `op.Path`, which is only populated when the operation states a `path:`, so
  `update` with `ref:` and no path saw an empty extension, matched neither the
  inferred nor the refused set, and wrote base32 filler over a `.exe`. That is
  exactly the silent wrong output the check exists to prevent. Proven fixed by
  dry-run before and after: `random_bytes:1024` became `format:pe`.
- **Attachment `Content-Type` came from the host.** `mime.TypeByExtension` reads
  `/etc/mime.types` on Unix and the registry on Windows, so `.txt`, `.zip`,
  `.docx`, `.csv` and `.eml` attachments were typed differently on different
  machines — against the reproducibility contract. Now a pinned table in the
  product, with no change to any shipped golden.
- **`model.Tree.Rename` could corrupt the tree.** It removed every moved object
  from its indexes in one loop and reinserted in a second that could fail
  part-way, leaving objects at neither path while `simulate` carried on against
  the wreckage. It now validates every collision before mutating anything.
- **`(stopped after 50 errors)` was printed when nothing had been dropped**, so
  an input with exactly 50 problems was told errors had been suppressed.
- **A PE section named `.idata` or `.rsrc` was silently overwritten** by the
  sections `BuildPE` appends and back-patches by name. `checkPe` now rejects
  the reserved names.
- **`runJobs` did not deliver the determinism its doc claimed** — the error
  returned was the lowest-numbered among the jobs that had *started*, which
  depends on scheduling. The code was fixed rather than the comment.
- **Two discarded parse errors.** `20000w` overflowed int64 nanoseconds to a
  negative duration that flowed into `baseTime.Add`; a 20-digit `delete_lines`
  passed validation as `MaxInt` because `strconv.Atoi`'s range error was
  dropped and Go returns a clamped value.
- **Archive problems were filed under the wrong YAML key**, so the line and
  column pointed at whatever chose the target rather than at `archive.members`.
- **A latent unsoundness in the Windows stream walk.** The buffer handed to
  `GetFileInformationByHandleEx` was stack-allocated and worked only by luck of
  escape analysis; adding any bounds check reproducibly broke the syscall with
  `ERROR_NOACCESS`. Fixed with `runtime.Pinner`, after which the bounds checks
  the walk was missing apply safely.
- **`pathpolicy.Source` was platform-dependent** inside a package whose doc
  promises the rules are identical everywhere: `filepath.IsAbs` made
  `Source("C:/evil.txt")` external on Windows and an error on Linux. A drive
  letter is now external on every OS, with a test for it.
- **`runinfo.writeAtomic` was not atomic** — no `Sync` before the rename, a
  fixed `.tmp` name two runs sharing a `--meta` directory would clobber, and the
  temp file left behind on failure.
- **`schema.typeToSchema` silently accepted anything it did not understand**,
  returning an empty schema that constrains nothing. It now panics, so a new
  `spec` type cannot quietly publish a broken schema.
- **`tools/gate` leaked its temp directory on every failing run**, holding up to
  eight cross-compiled binaries, because `os.Exit` skipped the deferred cleanup.

## P4: artefacts forensic tools can actually parse (b44fe70)

Generator version: **5**. Every file whose extension promises a format now
holds one, so the bytes of those files change, and so do the examples that
write them. The dry-run listing changes with them (it carries each
operation's content digest).

P0 made fsagen refuse to write base32 text into a file called `.exe`. This
phase replaces most of those refusals with a generator, and keeps the refusal
where there is none.

### Typed content

- **The extension picks the format** when a `create` or `update` gives no
  content of its own: `.exe` `.dll` `.sys` `.scr` build a PE, `.zip` `.jar` a
  zip, `.png` a PNG, `.jpg` `.jpeg` a JPEG, `.mp4` an MP4 and `.docx` an
  OOXML package. `format:` says so outright, and adds `chrome_history`,
  `firefox_places` and `text`.
- **`.pdf` is still not inferred.** A PDF's dates are settled while the
  operation is compiled, before its path has been rendered, so it stays an
  explicit `format: pdf` — which is what the P0 error already suggested.
- **Still refused, with a reason and a suggestion**: `.xlsx`, `.pptx`,
  `.gif`, `.bmp`, `.mov`, `.sqlite`, `.db` (use `format: chrome_history`),
  `.eml` and `.mbox` (use `action: email`).
- **PE** (F-GEN-3): PE32 and PE32+, for amd64, i386 and arm64; console, GUI
  or native; EXE or DLL; a TimeDateStamp the scenario sets (`"0"` included,
  which is what a reproducible build writes); named sections with
  characteristics; an import table written as `dll!function`, from which
  tools compute a stable imphash; a VS_VERSIONINFO resource; and a Windows
  checksum, which `TestPEChecksumMatchesWindows` compares with what
  `imagehlp!CheckSumMappedFile` computes for the same bytes. What fsagen
  writes is a container for a parser to read: there is no code in the image
  beyond the standard DOS stub, and the entry point points into filler.
- **zip, PNG, JPEG, MP4, docx**: `archive/zip`, `image/png`, `image/jpeg`, a
  box walk and an OOXML reader each read their own back in the tests.
- **`content_len` is the size of the filler region, not of the file.** A
  structured file carries it where such a file carries a payload: the PE
  overlay, a zip member, a private PNG chunk, JPEG comment segments, the MP4
  `mdat`, and for `pdf` and `docx` the document's text. With no
  `content_len`, a structured format writes the smallest valid file.
- **`content_kind`** (F-GEN-8): `text` (the default, today's base32),
  `bytes`, `zeros`, `pattern` or `lorem`. It says what invented bytes look
  like, so a scenario can ask for something that does not compress rather
  than for text that does.

### Browser history, and the epoch it was getting wrong

`format: chrome_history` and `format: firefox_places` (F-GEN-5) take a
`history:` block of visits — url, title, time, transition, `from_visit` — and
Chrome also takes downloads. They write the tables a parser queries, with
their indexes: Chrome's `meta`, `urls`, `visits`, `downloads`,
`downloads_url_chains` and `keyword_search_terms`; Firefox's `moz_origins`,
`moz_places` (with a reversed `rev_host`) and `moz_historyvisits`.

**The epochs were wrong before**, which the audit found (F-GEN-5) and the
code itself admitted in a comment: both databases were filled with Unix
seconds. Chrome counts
microseconds from 1601-01-01 and Firefox from 1970-01-01, so every visit in
a generated Chrome profile read back as a date in 1601 — not a rounding
error but four centuries. `TestChromeWebKitEpoch` and `TestFirefoxPRTime`
now pin each engine's own epoch against a fixed scenario time. Writing the
fix turned up a second bug of the same shape: 1601 to 2024 is about 423
years, past what a `time.Duration` holds, so the first version of
`chromeTime` overflowed and returned the same number for every visit. It is
integer seconds now, and the test caught it. `TestBrowserHistoryTimestamps`,
which read the value back as Unix seconds and so asserted the bug, is gone.

Bulk mode's profiles use the names a tool looks for — `Default/History` and
`Profiles/<name>.default-release/places.sqlite` — inside an invented profile
directory, instead of a random name with a `.db` or `.sqlite` extension.

### Two new actions

- **`archive`** (F-GEN-2, CR-7) writes a zip of files the scenario has
  already created. Members come from `member_refs` (every live path under an
  id, in creation order) and then `members` (glob patterns, in path order),
  deduplicated; `base` is stripped from the stored names; `comment` sets the
  archive comment; `method` is `store` by default, because deflated bytes
  come from `compress/flate` and so hold only for the pinned toolchain.
  Members are resolved from the model before the archive object exists, so a
  pattern can never sweep the archive into itself, and each member's stored
  time is the time the scenario gave that file. A member that does not lie
  under `base` is an error: fsagen will not invent a name for it. The
  members are read through quiet handles, so archiving a corpus does not move
  its access times.
- **`edit`** (F-GEN-9, CR-9) changes a file in place: `delete_lines` (a
  1-based inclusive range), `delete_matching` (a regular expression over
  whole lines), `replace` (a regular expression with `$1` expansion and an
  optional count) and `insert_after`. The steps run in that fixed order
  whatever order they are written in, and the file's line endings and its
  missing final newline survive. A range past the end of the file is an
  error. This is how a log gets a real gap in it rather than a truncation a
  tool can see at a glance.

### Smaller things

- **`template: email` is a real message** (F-GEN-7 remainder). It was a
  hand-written imitation with LF line endings, no Message-ID and no MIME
  headers. It goes through `email.Build` now, like `action: email`, and
  `net/mail` reads it.
- **Email attachments take a `ref`** (reusing P0's ids), so a message can
  attach a file an earlier step generated without naming its path. A ref
  that names more than one live path is an error, because a message attaches
  one file at a time.
- **`${IP:10.0.0.0/8}`** (F-DOC-3) draws an address inside a block from the
  operation's stream. IPv4 blocks with room to spare leave out the network
  and broadcast addresses. Bare `${IP}` keeps its 192.168.x.y walk.
- **fsagen writes its own zip files.** `archive/zip` always emits a data
  descriptor and leaves the sizes out of the local header, which real-world
  zips mostly do not, and exact size arithmetic is needed to place
  `content_len` filler. The docx writer moved onto it as well, and gained
  the two `docProps` parts, so a document now carries the title, author and
  dates a metadata tool reports. (`gingfrederik/docx` went in P1; this is
  the rest of D-10.)
- **A PNG's zlib stream is hand-rolled** from stored blocks, so PNG bytes do
  not depend on the Go release. JPEG, deflated zip members and SQLite
  databases do; the determinism contract says which.

### Deviations from the plan

- The plan padded a zip with its **archive comment** and an SQLite file with
  **page padding**. A zip gets a filler member instead, which is where a real
  archive carries bytes, and a history database takes no `content_len` at
  all: it is as big as its contents make it, and padding a database is not a
  thing a browser does.
- There is **no `format: eml` or `format: bytes`**. `action: email` writes
  messages and `content_kind: bytes` writes uniform bytes; a second way to do
  either would be a second thing to test.
- The plan allowed `delete_lines` to take a regular expression. It is

## P3: timelines and ground truth (03ce79a)

Generator version: **4**. File and stream contents and the dry-run listing are
unchanged for every example (the v4 goldens equal v3's). The ledger gains
fields, the answer key is new, and the modelled timeline is a new covered
output, which is why the version moves. `testdata/golden/v1` to `v3` are
removed: no test read them.

### Timelines

- **Four times per entry, each from its own source** (F-TL-2): access,
  modification, metadata change and birth, read with `FILE_BASIC_INFO` on
  Windows, `statx` on Linux (birth only where `STATX_BTIME` is reported) and
  `lstat` on the BSDs. Before, a third column held the creation time on Windows
  and the change time elsewhere, and the bodyfile wrote it as both ctime and
  crtime. An unknown time is 0 in the bodyfile and never copied from another.
- **Every named stream is its own record** (F-TL-4), `name:stream`, with its
  size and MD5 and its file's times, as The Sleuth Kit lists them.
- **The bodyfile is The Sleuth Kit's** (F-TL-6): names with a leading `/` and
  no root entry, TSK mode strings, `0` for an MD5 not computed, real inode
  numbers (the MFT record number on NTFS) and, on Unix, UID and GID. Files
  are hashed as streams of any size; `--hash-limit N` is the explicit cap
  (the silent 100 MB cut-off is gone). A name with `|` or a line break is an
  error, not a broken line. On Windows the mode is written as TSK writes it
  for NTFS.
- **MACB groups an entry's times by instant** (F-TL-7): one line per entry
  and distinct time, with `MACB`, `M.C.`, `...B` and so on.
- **A walk error is an error** (F-TL-8), naming the path, instead of a
  silently shorter timeline; the timeline is built in full before its file is
  written. Stream digests now go through quiet handles as well.
- **`--timeline-source modelled`** (D-2, F-TL-5): the timeline the scenario
  intends, built from the model and the ledger without reading the disk. It
  lists deleted objects as `name (deleted)`, its inode column is the ledger's
  object number, and it is the same bytes on every run with the same inputs
  and capability set, in every format. `--timeline-source observed` (the
  default) is the old behaviour, read back from disk.
- **New format `jsonl`** (`.jsonl`); CSV and text rewritten for the four
  times and streams. The text formats say which source they are; the run
  manifest records the source, format and file name of the timeline, and the
  digest of a modelled one.

### Ground truth

- **`answer-key.jsonl`** in the sidecar, derived from the ledger and the
  model: every object `created`, `modified`, `renamed` (with `from`) and
  `deleted`, every `stream` written, every `stomped` (a `mace`, with the
  fields it set), and every object that ends with an `mtime_before_crtime`.
  Only a complete run has one; its digest is in the run manifest.
- **Ledger** additions: `md5_after` and stream `md5` (for timelines),
  `kind` on a delete, `stream` on `ads`/`motw`, `moved` on a rotate (the
  object moved aside), and `explicit` (the time fields an operation stated
  and that were applied).
- **API:** `manifest.ExecuteFile` returns a `Result` (ledger, model,
  capabilities) with `Timeline()` and `AnswerKey()`; `compile.Options` gains
  `SkipUnsupported`; `timeline.Generate` takes `Options`; new
  `timeline.Modelled`, `ledger.AnswerKey`; `sandbox.FS.Meta` and
  `OpenStreamQuiet`.

### Fixes to earlier phases, found by running on Linux and Windows 10

The suite had only run on the Windows 11 development machine. Run on the lab
VMs (Fedora 40 and Windows 10 22H2), it found:

- **Verify failed on volumes that keep whole seconds** (P2). On Unix the time

  (what `mkfs.ext4` picks below 512 MB) and ext3 every fraction of a second a
  scenario asked for (`subsecond_jitter`, `start: now`) failed the run. The
  resolution now comes from the output directory's change time, which only
  the kernel sets; FAT and exFAT are known by name.
- **Tests that could not run on Linux** (P2): four time tests asked for
  creation times or streams before checking the platform, and the example and
  determinism tests did not skip unsupported operations. They now check first,

- **Linux goldens** recorded on Fedora: every example's files are
  byte-identical to Windows', less the NTFS streams.
- **Modes**: an explicit `mode` on a directory `create` now applies to that
  directory only (missing parents get `0755`), and a `rotate`'s `mode` is set
  exactly rather than narrowed by the umask. Unix metadata only.

## P2: timestamps that mean what the scenario says (af6356e)

Generator version: **3**. File and stream contents are unchanged for every
example (the v3 content goldens equal v2's); only a `copy` of a file with
streams gains those streams. The dry-run listing now shows each operation's
intended times, the run manifest gains time capabilities, and the new ledger
is a covered output, which is why the version moves.

### Times

- **All four times come from the scenario.** Each operation happens at a
  time T and sets the times of what it creates or changes by fixed rules,
  listed in README's new *Timestamps* section and in `compile/times.go`:
  creation makes everything T; writes set access, modification and change
  and keep creation; `mace` sets only what it names; `ads`/`motw` leave the
  file's times alone; rename keeps them and sets change; rotate keeps the
  rotated file's times; a copy is born at T with its source's mtime; a
  directory's modification and change times follow the last entry added,
  removed or renamed in it. Explicit times always win.
- **New fields `ctime` and `crtime`** (change and creation time) on create,
  update, append, truncate, mace, copy, email and ansible-vault. `mace` now
  needs at least one of the four times. On Windows they are set, with the
  access and modification times, in one `FILE_BASIC_INFO` call on a handle
  opened relative to the output root. The spike that decided the capability
  matrix: NTFS stores a change time set this way exactly
  (`TestChangeTimeSticks`); FAT does not store one.
- **Capabilities, never faked.** An explicit `crtime` or `ctime` where it
  cannot be set (Linux, macOS; `ctime` on FAT) fails pre-flight, naming the
  line and field; `--on-unsupported=skip` performs the operation without it
  and records the dropped field in the run manifest. A time the scenario
  only implies is listed as `uncontrolled` in the ledger.
- **Reference times.** A manifest operation happens at its `mtime`, else its
  `atime` (new), else `start`. One with none of them leaves its times to the
  file system; before, it did too, but nothing said so.
- **Playbooks no longer copy the scheduled time into `atime`/`mtime`.** The
  fields hold only what the author wrote. Behaviour changes that follow: a
  `mace` naming only `mtime` no longer also sets the access time (v2 set both
  to the one value), and an `ads`/`motw` keeps the file's times instead of
  stamping it with its own scheduled time (F-TIME-3). The `mace` change
  applies to manifests too. Other manifest operations that give only one of
  `atime`/`mtime` still get it for both, because that time is their T.
- **`delete`** stamps the object with its final times just before removing
  it, so what is left on disk carries scenario times. Its `atime`/`mtime`
  still set the directory it leaves; on a file at the top of the output this
  is now an error, since the output directory's own times are never set.
- **`rotate`** keeps the rotated file's times; v2 stamped both files with the
  rotate time (N-7). **`copy`** carries named streams, as the Windows
  `CopyFile` does, and keeps the source's mtime; v2 dropped the streams and
  stamped the op time (N-7).
- **Fractions of a second** are kept end to end (RFC 3339 with nanoseconds,
  100 ns on NTFS). A playbook's `subsecond_jitter: true` adds a seeded
  fraction of a second to every derived time, never to an explicit one
  (F-TIME-5).
- **Settle and verify.** After each operation fsagen stamps what it touched.
  After the last, it stamps the whole tree again, files first and then
  directories deepest first, and reads every time back. Any time that
  differs by more than the volume's resolution fails the run with a list.
  Only access times may be settled again, a few times, after a short pause:
  with last-access updates on, another process reading the new files (on
  this machine, Defender scanning a new `.bat` in a Startup folder) moves
  them. If they keep moving, the error says why.

## P1: determinism you can state in one sentence (31b10e1)

Generator version: **2**. Output changes for every seed. Corpora made by
version 1 are reproduced with the build that made them (tag 7accc8d and
62d759c before landing this).

README's *Determinism contract* is the statement: for one generator version,
the pinned toolchain, the same seed and the same inputs, file and stream
contents, paths, the dry-run listing and `run-manifest.json` are
byte-identical, on every platform, for every operation the platform supports.

### Output bytes

- **Every random value comes from its own keyed stream** (new `prng`
  package). A stream's key comes from the seed plus what the value is for:
  - the operation's `id`, or else a hash of its YAML;
  - for playbooks, the actor, step offset, iteration and batch;
  - the field;
  - the token kind and its position among tokens of that kind in the field.

  Adding, removing or reordering an unrelated action, field or token no
  longer changes any other value. Skipping an unsupported operation changes
  nothing else, so v1's placeholder draws (`drawOnly`) are gone. ChaCha8
  (`math/rand/v2`) supplies the bits. Text, hex, UUIDs and bounded integers
  are mapped in fsagen's own code, not by math/rand helpers that may change
  between Go releases. `TestPRNGGoldenVectors` pins the scheme.
- **Nothing reads the wall clock:**
  - A manifest's `${DATE}` uses the operation's `mtime`, else the new
    top-level `start`. With neither it is an error (v1 used the current
    time).
  - Unpinned `format: pdf` dates and an email with no `date` default to the
    scheduled time in playbooks, and to `mtime`/`start` in manifests. If
    one pdf date is given, the other copies it. With no reference time
    these are errors. v1 used the current time, or left an email without a
    `Date` header and dated its mbox entry 1970.
  - Bulk mode takes `--bulk-start` (default 2021-01-01T00:00:00Z) for its
    JSON, PDF, log, mail, zip and history dates.
  - Only `start: now` reads the clock, and it marks the run
    `"reproducible": false`.
- **`content: ''` writes an empty file.** v1 wrote 1024 random characters, and
  P0 refused it. Random content is used only when an operation gives no
  content, content_file or template.
- **Repeated email, pdf and vault specs are copied per occurrence.** Each
  occurrence renders its own tokens and gets its own date. v1 rendered the
  first occurrence in place and every later one reused it.
- **Playbooks run in time order.** Operations are stable-sorted by scheduled
  time, and ties keep declaration order. Overlapping repeating steps now
  interleave; before, one step ran to completion before the next started
  (F-IN-15). `${SEQ}` still counts in declaration order. In the examples,
  `playbook-insider-threat-exfil` and `playbook-malware-lifecycle` run in a
  different order.
- **`refs` over several files draws random content per file**, keyed by path.
- **The vault salt** comes from the operation's own stream when `salt` is not
  given.
- **Bulk mode is reproducible:**
  - The plan (directories, names, per-file keys) is built in one sequential
    pass.
  - A bounded worker pool renders each file in memory and writes it through
    the output root. Every worker is waited for on success and on failure.
    The error reported comes from the first failing file in plan order.
  - SQLite databases are built in a private temporary directory with no
    journal and then copied in, so stray `-journal` files are gone.
  - `.docx` comes from fsagen's own OOXML writer: stored members in a fixed
    order. The docx library it replaces wrote its members in Go map order,
    so the same seed gave different bytes. This writer was planned for P4
    and moved here for that reason.
  - `.mp4` is still placeholder text, now written directly.
  - The 19-versus-20 goroutine count mismatch and the nil-file writes after a
    failed create are gone with the old code (F-DET-1/2, F-GEN-6).

### New

- **`SHA256SUMS`** in the sidecar directory: every file and `path:stream`,
  sorted, in `sha256sum` format. `run-manifest.json` records its digest and
  counts.
- **`run-manifest.json` is deterministic:**
  - These moved out of it: module version, VCS revision, OS, architecture and
    file system.
  - It keeps the Go version and the capability set.
  - The non-reproducible facts go to the new **`run-info.json`**: build,
    host, platform, absolute paths, start and finish times.
- **`--bulk-start`**, and a top-level **`start`** for manifests (also in the
  schema).
- **Timelines** are written in UTC, sort equal times by path, and carry no
  `Generated:` wall-clock line. They record the live file system and remain
  outside the contract.
- **Pinned toolchain:** `go.mod` has `toolchain go1.27.0`. PDF streams and PNG
  output go through compress/flate, so a different Go release may change
  their bytes; the run manifest's `go_version` says which one was used.
- **Dependencies:**
  - `glebarez/sqlite` (GORM) is replaced by the plain `database/sql` driver
    `glebarez/go-sqlite`;
  - `gingfrederik/docx` is replaced by fsagen's own writer;
  - `abema/go-mp4` is dropped: it only passed bytes through. A real container
    is P4.
- **API:** `manifest.ExecuteManifest`/`ExecutePlaybook` now take
  `compile.Options`, which carries the seed. The global generator
  (`util.Seed`, `GetRandom*`) is gone. `util.AnsibleVaultEncrypt` requires a
  salt.
- **Schema:** a new test checks that the hand-written top-level keys match
  the Go types. Without it, `start` would have gone missing from the
  manifest schema unnoticed.

### Goldens

goldens under `testdata/golden/v1/` are no longer read by any test. They are
kept until the owner decides whether to remove them; the tags reproduce them.

### Deferred

## P0: stop silent wrong output and unsafe writes (b4a5d3e)

Generator version: **1** (unchanged bytes for valid inputs; see below).

This is the first phase of the correctness overhaul planned from the Mutant
QUILLDROP audit (`plan.json`). Its rule: every input mistake becomes an error
reported before anything is written; nothing is written or read outside its
root; timeline format and exit codes are honest.

### Output bytes

For every input that is still valid, output is byte-identical to 7accc8d.
`TestExampleContentGoldens` records names, contents and NTFS streams for all
15 shipped examples at seed 42. The v1 goldens were taken from 7accc8d's
behaviour and cross-checked against an unmodified 7accc8d binary before any
behaviour changed. Eight examples only gained `format: text` markers, and
their bytes are unchanged. The examples listed under *Examples* changed
because their inputs changed.

### Breaking: inputs that now fail

Each error names the file, line and column, the operation or step/action, and
the field.

- **Keys:**
  - unknown or duplicate keys, with the list of valid keys;
  - keys the action does not use (per-action field matrix, `compile.Fields`).
- **Values:**
  - a non-RFC 3339 time (atime, mtime, `pdf.created`/`modified`, `email.date`, `start`);
  - a negative `every`; `repeat` above 1 without `every`;
  - `repeat`/`batch_count`/`content_len` below 1;
  - `zone_id` outside 0-4; an invalid `mode`; line breaks in `host_url`/`referrer_url`.
- **Closed sets:** action names, `type`, `format`, conditions and templates.
  Action and condition names are now case-sensitive.
- **Tokens:**
  - an undefined `${VAR:x}` (was left verbatim);
  - an unknown, zero-length or unterminated token;
  - `${ACTOR}` in a manifest.
  - `$${` writes a literal `${`.
- **Template:** `template` together with `content`/`content_file` (the template
  used to win silently); an unknown template (was 256 random characters).
- **Existence:**
  - `delete` of a missing path (use `missing_ok: true`);
  - `update`/`truncate` of a missing file (use `create`);
  - `ads`/`motw` on a missing base;
  - `rename`/`copy`/`rotate` onto an existing path;
  - deleting a non-empty directory.
- **Paths:** `..` that leaves the root, absolute paths, drive letters, `:`,
  `\`, NUL, and names ending in a dot or space.
- **Portability** (waived by `--allow-nonportable`): reserved Windows device
  names, paths that collide by case or Unicode normalisation, relative paths
  over 200 characters.
- **Sources:** `content_file`, email body files and `attachments[].source_file`
  outside the YAML's directory (waived by `--allow-external-sources`);
  `source_root` must name a file already in the output.
- **Random content under a structured extension** (`.exe`, `.zip`, `.png`,
  `.jpg`, `.sqlite`, `.docx`, `.mp4`, `.eml`, ...). Use `format: text` for a
  deliberate placeholder.
- **`content: ''`** (explicitly empty). Generator version 1 writes random text
  for empty content. Until the next byte-changing version fixes that, it is
  refused rather than answered with 1024 characters of base32; `append` creates
  a missing log.
- **Playbooks** must state `start` (RFC 3339 or `now`).
- **Unsupported operations** (`ads`/`motw` where the volume has no named
  streams) fail before anything is written unless `--on-unsupported=skip`.
- **Command line:**
  - an output path that is a file;
  - a non-empty output directory without `--clean` or `--into-existing`;
  - a timeline with an unknown extension, or inside the output directory;
  - timeline-only mode on a missing directory.

### New

- **Module path** `github.com/aoiflux/fsagen`, so `go install` works once pushed.
- **References between actions:** `id`, `ref`, `refs`, `missing_ok`.
- **Flags:**
  - `--validate`, `--dry-run` (JSON lines);
  - `--clean`, `--into-existing`, `--on-unsupported`;
  - `--allow-nonportable`, `--allow-external-sources`, `--meta`;
  - `--timeline-format` (`.body` is now a bodyfile);
  - `--version`.
- **`run-manifest.json`** beside the output (`<out>.fsagen/`). Its status is
  `running` until the run ends, then `complete` or `failed` with the failing
  operation. It also records the generator version, seed, SHA-256 of every
  input, options, platform, filesystem and skipped operations. It contains no
  absolute paths or wall-clock times.
- **Exit codes:** 0 success, 1 generation failed, 2 command-line error.
  Diagnostics go to stderr.
- **Confined I/O:**
  - every manifest/playbook write goes through `os.Root`;
  - NTFS streams are opened relative to a handle on their base file
    (`NtCreateFile`), so they can only belong to a file inside the root;
  - streams are enumerated with `FileStreamInfo`.
- **Tooling:** JSON Schemas generated from the validator's own field table
  (`schemas/`, drift test), MIT `LICENSE`, `.gitattributes`, and
  `go run ./tools/gate`.
- **Platforms:** builds for darwin and freebsd (the timeline stat reader is
  split per OS).
